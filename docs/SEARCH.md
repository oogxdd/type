# Поиск в Type

## Первая реализация: grep по файлам

Решение после обсуждения с пользователем: искать прямо в Markdown-файлах.
Не добавлять SQLite, embeddings или индекс всего корпуса в памяти.
На старте приложения и при открытии пустого поиска нет обхода заметок.

На GPUI desktop: кнопка лупы рядом с фильтром Stream / Folders, Cmd+Shift+F
(Ctrl+Shift+F вне macOS), либо Search notes в палитре.
Ввод запускает поиск после паузы 180 мс. Стрелки выбирают результат,
Enter открывает заметку, Esc / клик снаружи закрывает окно.
Текущий черновик сохраняется перед открытием поиска; конфликт сохранения
оставляет черновик и препятствует открытию поиска.

- Буквальные подстроки без учёта регистра, с Unicode case-insensitive matching. Все слова
  запроса обязательны, могут встречаться на разных строках или в пути.
  Это не regex, нечёткий поиск или морфология; кавычки не задают фразу.
  Unicode normalization, ё/е и полное Unicode case folding пока отсутствуют.
  Matcher использует Rust regex с экранированными литералами: regex-синтаксис
  в пользовательском запросе не исполняется.
- Поиск по полному телу и относительному пути; frontmatter не участвует.
  Результат: заголовок, путь, отрывок возле первого совпадения.
- Область: активный профиль, Stream и пользовательские папки, включая заметки
  с `archived_ms`/`reviewed_ms`. Физическая корзина `_system/archive`, остальные
  внутренние `_system`-папки, корневой AGENTS.md и dot entries исключены.
  Обычные Open Folder tabs и мобильные оболочки пока не подключены.
- Сканирование выполняется в background executor, по одному файлу за раз.
  Обход не строит навигационное дерево и не читает все тела заранее.
  Используются существующие core read/decryption и frontmatter codec.
  Внешние grep/rg устанавливать и запускать не требуется.
- Сохраняются максимум 100 результатов, общий счётчик охватывает все совпадения.
  Порядок детерминированный по путям при обходе папок; relevance ranking нет.
  В UI одновременно рисуется максимум 6 строк, стрелки позволяют пройти 100.
  Более узкий запрос позволяет найти результат за первым лимитом.
- Новый ввод отменяет предыдущий запрос; флаг проверяется между файлами и
  папками. Уже начатое чтение одного файла не прерывается. Номер поколения
  препятствует показу старого результата после нового ввода, закрытия,
  блокировки или смены профиля. Это не атомарный снимок файловой системы.
- Ошибки чтения отдельных файлов считаются и отображаются как unreadable files;
  ошибка обхода каталога отображается отдельно. Symlinks не обходятся.
- Новые запросы видят внешние изменения сразу. Уже показанный результат
  обновляется при следующем запросе / повторном открытии и вводе.
- Содержимое не кэшируется и не пишется на диск. Для encrypted notes поиск
  доступен после разблокировки, результаты сбрасываются при блокировке.
  Закрытие окна отменяет работу и удаляет выдачу. Поиск ничего не отправляет
  в сеть. Это локальный пользовательский поиск, не MCP-проекция для агентов.

Стоимость запроса — O(суммарного объёма текстов), а не только числа файлов.
Оперативная память — текущий файл, список записей текущих
каталогов и ограниченная выдача; весь корпус не удерживается.
Очень большие отдельные файлы увеличат задержку отмены и потребление памяти.

## Проверка 3000 заметок

`search::tests::benchmark_3000_notes_on_disk` создаёт отдельный временный
профиль с 3000 файлами примерно по 18 КБ (~54 МБ), затем выполняет шесть
запросов: частое совпадение, отсутствие, уникальная подстрока в конце файла,
несколько слов, регистр, путь. Используются настоящие core-чтения.

Команда для воспроизведения:

```sh
cargo test -p type-gpui --lib search::tests::benchmark_3000_notes_on_disk -- --nocapture --test-threads=1
```

Замеры ниже должны интерпретироваться как локальные: файловый кэш ОС уже
прогрет созданием fixture, это не cold-cache тест и не измерение production
заметок. Время 180 мс debounce прибавляется к времени сканирования.
Замер 2026-11-11 на этом Mac, debug/test build без debug symbols:
208–216 мс на полный запрос по ~54 МБ (шесть разных запросов); с debounce
примерно 388–396 мс до выдачи. Это один прогон, не оценка p95.
Начальный вариант с lowercase-копией каждого тела занимал 578–762 мс;
скомпилированные Unicode case-insensitive literal matchers убрали это копирование.
Проверки UI покрывают задержку ввода, переход к заметке, сохранение черновика,
замену запроса, закрытие и поглощение клика фоном.

## Как развивать поиск при необходимости

Это план, а не установленная зависимость или обязательная миграция.
Сначала собрать реальные сценарии и замеры: время до результатов, p50/p95
сканирования, объём корпуса, большие файлы, частые запросы. Рабочая цель для
~3000 обычных заметок — p95 до 300 мс на само сканирование на целевом Mac;
если не выполняется, сначала профилировать traversal/read/decode/matching.

### 1. Улучшить обычный поиск

Следующие полезные функции: scope по папке, теги/даты, отдельное включение
Trash, поиск фраз, подсветка и переход к конкретному месту в заметке.
Затем relevance: точный заголовок → слова в заголовке → тело, с понятными
детерминированными tie-breaks. Проверять русские и английские запросы.

Если измерения покажут, что повторный обход слишком дорог, рассмотреть
постоянный локальный SQLite FTS5 индекс. FTS5 предоставляет полнотекстовый
поиск, BM25, snippets, prefix queries и отдельный trigram tokenizer для
подстрок. Выбор токенизатора важен: обычный token search меняет нынешнюю
семантику подстрок, а stemming для русского требует отдельного решения.
Источник: [SQLite FTS5](https://www.sqlite.org/fts5.html).

Markdown остаётся источником истины. База — производные данные в app data,
отдельно для каждого профиля; не коммитить её в Git notes и не синхронизировать.
Обновлять затронутые документы после save/create/delete/move/sync, следить
за внешними изменениями и иметь сверку после пропущенных событий.
Идентичность — UUID заметки, путь изменяемый; для legacy без UUID требуется
явная совместимость. Хеш текста позволяет не переиндексировать неизменённое.
Сохранять schema/tokenizer versions; перестройка только при несовместимости
или повреждении, с прогрессом и возможностью пользоваться приложением.

Для encrypted profiles обычную plaintext FTS-базу не создавать: остаётся
нынешний поиск после unlock, пока не спроектированы encrypted index и
обращение с WAL, временными файлами, backup и сменой ключа.

### 2. Добавить поиск по смыслу как опцию

Embeddings решают другую задачу: найти запись по перефразированному смыслу,
даже если слова запроса отсутствуют. Текст и запрос кодируются совместимой
моделью, затем сравниваются векторы. Это не замена точному поиску имён,
чисел и цитат. Источник: [Sentence Transformers: semantic search](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html).

Предлагаемый путь:

1. Собрать набор запросов с ожидаемыми заметками, включая RU/EN, короткие
   записи, длинные дневники, точные имена и смысловые перефразировки.
2. Сравнить локальные multilingual retrieval модели на этом наборе; измерить
   качество top-5/top-10, размер загрузки, RAM, CPU и query latency.
   Конкретную модель выбрать после сравнения, не фиксировать сейчас.
3. Короткую заметку кодировать целиком; длинную делить по заголовкам/абзацам
   с небольшим перекрытием, соблюдая tokenizer budget модели. Каждый chunk
   хранит UUID, область/смещение, content hash, model и chunker versions.
4. Индексировать изменения в фоне с отменой/повтором; первоначальную обработку
   сделать явной с прогрессом. При смене модели векторы пересчитываются.
5. Для нескольких тысяч заметок начать с точного cosine/dot-product поиска
   по нормированным векторам. Например, 30 000 chunks × 384 float32 — примерно
   44 MiB только векторов. Это оценка, число chunks надо измерить.
   Отдельный vector server и ANN пока не обязательны; вводить их после замеров.
6. Объединять keyword и semantic выдачи по рангу (например RRF), удалять
   дубликаты chunks одной заметки, показывать подходящий отрывок.
   Небольшой reranker — лишь если прибавка качества оправдает latency.
7. Хранить embeddings локально, считать чувствительными производными данных.
   Cloud embeddings — только отдельный явный opt-in с понятным составом
   отправляемых данных. Не переиспользовать пользовательский индекс в MCP:
   агентские данные должны отдельно проходить privacy projection / skip-ai.

### Условия готовности следующего этапа

Набор синтетических correctness/security fixtures; стабильная выдача при
переименовании, удалении и sync; отсутствие результатов после lock/profile
switch; измерения 3000 и более крупных корпусов; сравнение качества с текущим
сканированием. Локальный grep остаётся fallback, если индекс недоступен.
