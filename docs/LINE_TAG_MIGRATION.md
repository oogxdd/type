# Теги на строках: решение и возможная миграция

Статус: проектирование, не изменение текущего формата. 2026-09-08.

## Что есть сейчас

Заметка — Markdown с frontmatter. `type_selection_tags` содержит JSON версии 1:
`blocks: [{ index, hash, before, after, document, tags: [{ name, color }] }]`.
Индекс относится к текстовым блокам Tiptap (абзацам, заголовкам, блокам кода,
включая абзацы внутри списков), а не к строкам файла. Хеши — отпечатки текста
и соседей, не криптографическая защита. При редактировании теги живут на узлах
редактора; при сохранении обновляются привязки. Внешние изменения могут оставить
неразрешённые привязки. `skip-ai` — обычное имя кастомного тега, не текстовый маркер.

## Почему строки привлекательны для мобильного приложения

Логическая строка разделена LF (`\n`), не зависит от ширины экрана. Мобильный
редактор работает с текстом Markdown: позиции символов и изменения текста
естественнее сопоставлять со строками, чем воспроизводить дерево Tiptap.
Одинаковая модель может работать в Rust, на телефоне и в MCP без DOM.
Но одни номера не отслеживают изменения: адаптация мобильного редактора всё
равно должна обновлять привязки вместе с текстом. Простое сохранение старого
frontmatter после правки небезопасно.

## Предлагаемый контракт версии 2

Считать строки тела заметки без frontmatter; нормализовать CRLF в LF.
В интерфейсе считать с 1, в данных — с 0, конец диапазона исключительный:
`{ version: 2, coordinate: "body-lines-lf", bodyDigest, ranges:
[{ startLine: 7, endLineExclusive: 10, tags: [{ name: "skip-ai", color: "#8b5cf6" }] }] }`.
Это строки 8–10. До реализации определить семантику завершающего LF, пустого
тела и служебного backmatter. Лучше исключать служебный backmatter из пространства
координат и хранить это правило как часть версии. Digest должен быть
криптографическим и привязанным к точному нормализованному телу.

Во время редактирования удобнее отслеживать диапазоны позиций символов через
операции редактора, вычисляя строки при сохранении. Вставка трёх строк перед
диапазоном сдвигает обе границы на три; вставка внутри наследует тег; удаление
сокращает диапазон, удаление всего диапазона снимает назначение. Undo/redo должны
восстанавливать текст и теги вместе. Отдельно определить наследование на границах
и при Enter внутри строки. Для `skip-ai` предпочесть консервативное наследование.

При внешней правке использовать diff старого и нового тела. Без старого тела
потребуется контекст/отпечатки; повторяющиеся строки и перемещения неоднозначны.
При несовпадении digest без достоверной перепривязки MCP отклоняет заметку.
Digest обнаруживает устаревшие привязки, но сам по себе не восстанавливает их.

## Как мигрировать

1. Сначала добавить чтение v1 и v2 в обоих редакторах и MCP. Не интерпретировать
   неизвестную версию как отсутствие тегов. Устаревшие клиенты не должны писать
   новый формат: нужен минимальный поддерживаемый клиент или запрет редактирования.
2. Создать резервную копию до миграции. Сделать dry-run с числом успешных,
   неразрешённых и неоднозначных назначений, без текста приватных фрагментов в логах.
3. Для каждого v1-документа восстановить блоки точно тем же парсером, что редактор,
   и разрешить ВСЕ привязки. Получить соответствие узлов диапазонам исходного Markdown
   через source map. Простое `index -> line` неверно для списков, кода и переносов.
4. Каждый блок покрыть полными исходными строками. Если разные блоки делят одну
   строку, объединить теги: миграция может скрыть больше текста, но не меньше.
   Неразрешённые документы оставить в v1 и показать пользователю для проверки.
5. Сохранить v2 и тело атомарно, не переформатируя исходник. Записать отчёт миграции
   и обеспечить восстановление резервной копии. Повторный запуск должен быть идемпотентным.
6. Проверить равенство или более строгую фильтрацию v2 относительно v1 на корпусе
   примеров: кириллица/emoji, CRLF, пустые строки, списки, цитаты, код, дубли абзацев,
   внешние вставки/удаления, синхронизация, undo/redo.
7. После перехода клиентов переключить запись на v2. Избегать двух одновременно
   изменяемых копий тегов v1/v2: они неизбежно расходятся.

## Компромисс и текущее решение

Строки упрощают мобильный текстовый редактор и независимый сервер, но усложняют
нынешний визуальный Tiptap: сериализация Markdown меняет пробелы и переносы.
Нужна source map или Markdown-редактор, сохраняющий исходник, а не только новая
форма JSON. Сейчас оставляем v1 и реализуем MCP; проекцию для AI выделяем отдельно.
При миграции заменить разрешение привязок внутри проекции, сохранив MCP-контракт
list_notes/read_note/search_notes и одинаковую фильтрацию поиска и превью.
