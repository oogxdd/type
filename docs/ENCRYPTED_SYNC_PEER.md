# Encrypted sync peer (v1)

Type can use an always-online Linux peer as an encrypted mailbox. A phone uploads
while the computer is offline; the computer downloads later. Local notes remain
ordinary Markdown. This does not enable the optional local at-rest encryption.

## Linux VPS setup

Build on Linux using the repository's pinned Rust toolchain. The peer package
has no dependency on the notes core, libgit2, Tauri, Python, or a GUI.

```sh
cargo build --release --locked -p type-sync-peer
sudo useradd --system --home-dir /var/lib/type-sync-peer --shell /usr/sbin/nologin type-sync
sudo install -m 0755 target/release/type-sync-peer /usr/local/bin/type-sync-peer
sudo install -d -m 0700 -o type-sync -g type-sync /var/lib/type-sync-peer
sudo -u type-sync /usr/local/bin/type-sync-peer init /var/lib/type-sync-peer
sudo install -m 0644 deploy/type-sync-peer.service /etc/systemd/system/type-sync-peer.service
sudo systemctl daemon-reload
sudo systemctl enable --now type-sync-peer
```

`init` prints a **server setup code**, containing the endpoint identity and a
random access token. Repeating `init` prints the same code without resetting
storage. It does not contain a note decryption key: that key is generated by the
first app. Do not put the code in public logs. `serve` never prints the token.

Iroh uses its normal N0 discovery/relay configuration; allow outbound DNS and
HTTPS, plus UDP for direct connections. No domain name, public HTTPS endpoint,
or SSH Git service is required. An inbound UDP firewall can prevent direct paths;
the relay path remains available if outbound connections are permitted.

## Connect devices

1. Desktop **Settings → Sync → Encrypted sync peer**: paste the server setup code.
2. Wait for the first successful upload.
3. Choose **Pair another device**. The QR/code now includes the client vault key.
4. On the phone's **Sync → Encrypted sync peer**, scan that QR or paste the code.
   A second desktop can paste the same device code.
5. Keep a private recovery copy of the device code. The server cannot recover it.

The first setup code is only for an empty peer. Additional devices must use the
app's device pairing code; independently creating two keys does not work.
One peer data directory serves one notes vault. Use separate processes/data
directories for independent working folders. Configuration is device-local and
associated with the canonical notes root; moving that root requires reconnecting.

Desktop checks the peer every 30 seconds while Type is running. Mobile uses its
existing save/foreground triggers and retry loop, then checks every 30 seconds
while the process remains active. **Uploaded to peer** means the
peer durably stored the ciphertext, not that the other device received it.
Mobile background execution remains subject to the OS; this feature does not
keep iroh running indefinitely after iOS suspends the app.

## Data format and trust boundary

- Git commits, paths, frontmatter, note bodies, attachment data tracked by Git,
  manifests, and recording audio are encrypted on the client with
  XChaCha20-Poly1305 before Iroh receives them. Local files are never rewritten
  into the note-body encryption format.
- The 256-bit vault key is generated on a device and stored in app-data outside
  the notes root. Client config and server credentials use mode 0600 on Unix.
  Neither the vault key nor device credentials are sent as server configuration.
- Server objects are addressed by SHA-256 of **ciphertext**. Random AEAD nonces
  prevent predictable plaintext hashes from becoming server lookup identifiers.
  Associated data binds each envelope to its version, vault, and object kind.
- Authenticated manifests describe the Git commit, incremental Git packs, audio
  paths, and content hashes. All of that metadata is inside ciphertext. The
  server sees an opaque vault identifier, revision, ciphertext hashes, sizes,
  access times and connecting IPs.
- Clients remember an acknowledged manifest and verify its encrypted predecessor
  chain on subsequent syncs. Old or replaced history is rejected. A new device
  has no previous freshness pin; a malicious server can hide recent updates.
- Uploads are immutable. Atomic head compare-and-swap retries concurrent writers;
  clients merge Git locally and preserve conflicts as `.conflict` siblings.
  After a lost acknowledgement, retrying observes the already-published head.
- The access token is independent of the encryption key. The VPS can read its
  token but cannot decrypt objects. Anyone holding a device code can decrypt
  and write this vault. There is no per-device revocation UI in v1.

## Limits, backup and retention

The default quota is **10 GiB**, configurable as `quota_bytes` in
`/var/lib/type-sync-peer/peer.json` while stopped. Objects have a **256 MiB** limit
(including AEAD framing); manifests are limited to **8 MiB**. Git transfers are
incremental after the initial history upload. A legacy repo with a large audio
history may need the existing audio-history migration before its first upload.
Recordings are separate immutable encrypted objects; a conflicting recording
filename with different bytes produces an error instead of overwriting audio.

V1 retains encrypted history and orphaned uploads; it has no server garbage
collector. Quota exhaustion fails without publishing a partial manifest. Audio
is append-only and missing local audio is downloaded again. A peer receipt does
not count as the existing desktop audio-durability receipt, so it never authorizes
phone audio eviction. OCR/transcription still runs on a device with the key.

Future snapshot compaction and garbage collection are outlined in the
[retention implementation plan](ENCRYPTED_SYNC_PEER_RETENTION_PLAN.md).
That proposal is not implemented in v1.

Back up the entire peer data directory, preferably with the service stopped for
an atomic filesystem snapshot. Restore it together, including `peer.json` and
`head.json`; changing the endpoint identity requires pairing again. A restored
older snapshot is intentionally rejected by clients with a newer local pin.
Never delete object files manually: older incremental packs and manifest-chain
objects may still be required. Server backups contain ciphertext and server
credentials, but no client vault key. Losing all device keys and the recovery
code makes the peer copy unreadable.

Native mobile builds must regenerate the UniFFI module after this change:
`npm run codegen:ios -w @typenotes/mobile-core` (simulator) or
`npm run codegen:ios:device -w @typenotes/mobile-core` (physical iPhone).
