## Назначение и статус

Этот файл сохраняет исходный план **десктопных изменений** после compact.
Обязательные этапы реализованы 2026-10-06 в ветке
`feat/desktop-sync-performance`, worktree `.worktrees/desktop-sync-performance`,
на базе `669e23df`, коммит реализации `6f616b83`. Изменения мобилы, включая
формирование превью, делает другой
агент. Ниже сохранён исходный план; актуальный результат указан в следующем
разделе и в `GPUI_MIGRATION_STATUS.md`.

Цель: при уже синхронизированной базе обычный синк нескольких текстовых заметок
должен делать работу преимущественно для изменившихся файлов. Принятые заметки
должны быстро появляться в GPUI; сканирование очередей, аудио и обслуживание
кэшей не должны задерживать текстовый синк или интерфейс.

Продолжая работу, сначала прочитать `AGENTS.md`,
`docs/GPUI_MIGRATION_STATUS.md` и этот файл, затем проверить актуальный код и
`git status`. Ссылки на строки из предыдущего разговора могут устареть.

## Фактический результат реализации (2026-10-06)

- GPUI получает событие успешного push через канал; объединяет события,
  сохраняет pending refresh при lock/busy, проверяет поколение профиля и
  revision корня. Чистые buffers обновляются, dirty drafts/baselines сохраняются,
  в том числе при открытом folder workspace. Пустой и отклонённый push не
  запускают обновление UI.
- Refresh заметок отделён от processing queues. Повторно читаются только
  изменившиеся превью; fallback сверяет метаданные дерева раз в 15 секунд.
  Лёгкий статус host опрашивается раз в 3 секунды; очереди — отдельно при
  открытых соответствующих настройках, не чаще раза в 10 секунд.
- Receipts обслуживаются после готовности host в объединяющей фоновой очереди;
  сканирование/хеширование не блокирует Git или уведомление UI. Кэш не доверяет
  синхронизированному receipt без локальной проверки. Перед атомарной публикацией
  проверяются revision, исходный manifest и fingerprints файлов.
- Редакторы flush до server pre-commit. Reentrant write lease по каноническому
  корню охватывает короткие записи и incoming checkout/ref update. Сетевой
  обмен и custom post-receive не удерживают lease. UI сохраняет draft и
  повторяет сохранение при занятом lease. Поздняя tracked-правка отклоняет push
  с сохранением обеих историй; pull/merge/retry проверены. `updateInstead`
  сохранён; временные hooks применяются только к Git child, старые hooks
  продолжают работать. Завершение Git освобождает координацию независимо от
  SSH close/backpressure.
- Проверки: **105 core + 82 GPUI tests**, native dev build и отдельный bundle.
  Синтетическая база 6600 файлов: дневной delta push **1,593 с**, пустой push
  **0,386 с** по Mac loopback SSH. Receipts для 6601 заметки и одного аудио:
  cold **256 мс**, warm preparation **83 мс**, без дополнительных чтений тел
  или хеширования. Это не замер телефона/Iroh; прежние 129,626 с напрямую
  сравнивать с этим benchmark нельзя. Подробности проверок и логов в журнале.
- Dev bundle: `.tmp/desktop-bundle/bundle/Type GPUI Dev.app` в новом worktree.
  Текущее приложение не перезапускалось; личные заметки не использовались.
- Осталось: реальный замер новых native builds, пользовательская проверка UI,
  optional changed-path reconcile и согласованный desktop → phone revision
  signal. Linux/Windows runtime временных Bash hooks не проверен. Внешние
  процессы записи не участвуют в Rust lease; сохранены Git dirty checks,
  baselines и fallback. Не заявлять полную межпроцессную атомарность.
- При интеграции с мобильной веткой сохранить **reentrant**
  `application/workspace.rs`: API `with_workspace_write` совместим, но теперь
  есть вложенные guarded helpers, nonblocking try, revision и Git-active
  tracking. Нерекурсивный старый mutex вызовет deadlock. Чужие dirty files,
  mobile/FFI/TS-контракты в эту ветку не переносились.

На обоих устройствах база уже была; пользователь обычно синкает изменения за

Git-tracked аудио; синтетический benchmark с аудио не описывает личную базу.

Телефон сообщил следующий успешный цикл:

| Этап | Время |
| --- | ---: |
| Стартовый refresh статуса до автосинка | 18,504 с |
| Проверка статуса перед pull | 13,655 с |
| Native Git pull | 62,042 с |
| Обновление заметок после pull | 9,011 с |
| Native Git push | 44,512 с |
| Полный pull → push | 129,626 с |

На десктопе три `upload-pack` завершились успешно за 2,387 / 0,187 / 0,336 с.
`receive-pack` завершился успешно за 11,403 с. Уведомление о принятом push
появилось через 10,690 с после завершения Git child process.

сама по себе не доказывает такую же задержку push на телефоне. Оставшееся время
телефонного push пока не разделено на локальную работу и ожидание транспорта.

## Уже выполненная общая оптимизация

Коммит `669e23df` — `fix(sync): avoid repeated Git worktree scans and checkouts`:

- Сохраняется проверенный stat-cache Git index, вместо повторного хеширования
  неизменившихся файлов при каждом открытии repository. Есть fallback при
  невозможности записи cache и сохранена обработка отсутствующего skip-worktree
  аудио; реальные изменения не становятся staged от проверки статуса.
- Убраны повторные dirty scans перед `commit_all_changes`.
- Пропускается checkout уже текущей ветки; исправлена подготовка настоящего
  переключения ветки с сохранением защиты локальных изменений.
- Добавлены native тайминги статуса, commit, подготовки ветки, merge/checkout,
  pull/push, Git child process, SSH close и desktop receipt maintenance.

На синтетической базе 2000 заметок + 128 MiB legacy tracked audio повторный
status сократился с ~432 мс до ~11 мс после первого обновления cache, ненужный
checkout — с ~466 мс до <1 мс. Это доказательство устранённой работы на Mac,
а не измерение ускорения телефона. Для телефона нужен новый native build.

Проверки того коммита: 101 core test, 79 GPUI tests, форматирование, сборка
dev bundle. Не повторять изменения коммита как новую работу.

## Этап 1 — обязательные изменения десктопа

### 1. Подключить уведомление о принятом push к GPUI

Код:

- `crates/type-core/src/adapters/local_sync/mod.rs`:
  `PUSH_LISTENER`, `set_local_sync_push_listener`,
  `notify_local_sync_push_received`.
- `apps/gpui/src/workspace.rs`: запуск приложения, `refresh`, `poll_task`.
- Для сравнения: `apps/desktop/src-tauri/src/commands/mod.rs` уже подключает
  listener к старому shell; GPUI пока этого не делает.

Подключить серверное событие через безопасный канал на GPUI executor. Не
обращаться к UI из серверного callback. Событие должно быть привязано к корню
и поколению профиля: позднее событие старого сервера не обновляет новый профиль.
Проверить время жизни подписки, shutdown и возможность нескольких окон.

Объединять повторные уведомления. Если refresh сейчас выполняется или временно
нельзя применить результат, сохранить потребность в следующем обновлении, а не
потерять событие. Сохранить корректное поведение при active folder workspace,
locked state и переключении профиля. Нынешний `refresh` имеет ранние выходы,
а `revision` может измениться во время фонового чтения.

Первый шаг может использовать существующий refresh, если он уже отделён от
тяжёлых очередей. Следующий шаг — передавать набор изменённых путей и обновлять
только их. Изменение HEAD недостаточно для определения реальных изменений:
локальный commit тоже меняет HEAD. Учитывать добавления, удаления, переименования,
conflict-файлы, folder order и синхронизируемые настройки.

### 2. Разделить обновление заметок и состояния обработки

Код:

- `apps/gpui/src/workspace.rs`: опрос раз в 3 с и фоновая часть `refresh`.
- `apps/gpui/src/jobs.rs`: `processing_snapshot`.
- `crates/type-core/src/adapters/recordings/mod.rs`: `collect_recording_notes`.
- `crates/type-core/src/adapters/handwriting/mod.rs`: `collect_handwriting_notes`.

Сейчас каждый refresh вызывает список recordings, список handwriting, статус
import, полное дерево и обновление изменённых превью. Списки recordings/OCR
могут читать содержимое всей базы, даже когда цель — показать один полученный
текстовый файл или узнать число задач.

Разделить независимые задачи. Состояние обработки получать из кэша/событий
очередей или обновлять отдельно с объединением запросов. На первом этапе
достаточно убрать body scans из регулярного refresh; не требуется сразу
переписывать все processing adapters.

Для заметок предпочесть событийное обновление и инкрементальные изменения.
Внешние изменения через Finder/редактор по-прежнему должны обнаруживаться:
использовать watcher, если подходящий уже есть, либо оставить более редкое
восстановительное сканирование. Ошибка/переполнение watcher или пропущенное
поколение требуют полного reconcile. Не удалять polling без замены этой функции.

Не перечитывать превью неизменившихся файлов. Сохранить выбранную заметку,
ручной scroll, modal editor state и защиту dirty drafts. Полученный внешний
текст можно применить к чистому buffer; dirty buffer нельзя перезаписывать.

### 3. Убрать обслуживание аудио из пути готовности сервера и обновления UI

Код:

- `crates/type-core/src/adapters/local_sync/ssh_server.rs`: `pump_child_io`.
- `crates/type-core/src/adapters/local_sync/mod.rs`: запуск сервера.
- `crates/type-core/src/adapters/attachment_retention.rs`:
  `issue_desktop_audio_receipts`.

Сейчас успешный `receive-pack` закрывает SSH-канал, выполняет receipts и только
затем уведомляет frontend. При запуске сервера receipts выполняются до открытия
SSH/Iroh. Обслуживание собирает recording metadata по заметкам и хеширует все
существующие связанные аудиофайлы, включая уже подтверждённые.

Уведомлять GPUI после успешного применения push, независимо от receipts.
Запускать обслуживание отдельной фоновой очередью после готовности сервера,
объединять повторные запросы, не создавать неограниченное число задач.

Далее перейти к проверке новых/изменённых записей, с отдельным восстановительным
проходом. Не объявлять данные сохранными только по mtime/размеру: receipt
подтверждает hash реально полученных байтов. Сохранить отзыв подтверждений при
исчезновении/изменении аудио и правила безопасного удаления мобильного кэша.

Receipt manifest — tracked metadata: фоновая запись не должна внезапно пачкать
worktree во время `receive-pack`. Координировать её с Git apply и сменой профиля;
следующий fetch может получить новый manifest обычным способом. Не ждать этой
работы для объявления текстового push успешным.

## Этап 2 — координация записи и более бесшовная доставка

### 4. Устранить гонки autosave, server commit и Git apply

`ssh_server.rs` перед обслуживанием Git выполняет синхронный
`commit_all_changes` прямо из async handler и игнорирует ошибку через `let _`.
Вынести блокирующую работу с async executor и корректно завершать запрос при
ошибке подготовки repository. Сериализовать конфликтующие Git-операции на root.

Проверить новую общую `application/workspace.rs` и её использование другими
агентами. Mutex Rust сам по себе не защищает worktree от внешнего процесса
`git-receive-pack`, работающего с `receive.denyCurrentBranch=updateInstead`.
Нельзя считать гонку исправленной, просто обернув pre-commit этим mutex.

Нужна явная координация flush открытых редакторов, кратких изменений файлов и
применения incoming update. Не держать UI thread или общий write lock на всём
сетевом обмене. Если нынешняя схема updateInstead не позволяет короткую фазу
apply, отдельно обосновать более крупное изменение staging/apply; не заменять
архитектуру Git на другую систему ради этой задачи.

Не обещать, что ещё не сохранённый черновик уже отправлен. Конфликт с внешним
изменением сохраняет draft и baseline, а не молча затирает одну из версий.
Учесть профильные редакторы и открытые folder workspaces. Не вводить взаимную
блокировку server → UI flush → core write lock.

### 5. Уведомлять телефон о новых изменениях десктопа

Это дополнительный этап после устранения измеренных задержек. Сейчас desktop
host обслуживает запросы, а инициатор обычного цикла — телефон. Можно передать
по существующему авторизованному Iroh-соединению небольшой сигнал новой версии,
чтобы активный телефон запустил обычный Git-синк без ручного refresh.

Нужны согласованный мобильный обработчик и совместимость старого клиента:
сначала договориться с мобильным агентом о минимальном протоколе. Сигнал —
подсказка о необходимости pull, не второй канал записи Markdown. Объединять
частые autosave, не создавать echo loop от incoming push и receipt updates.
После reconnect нужна проверка состояния на случай пропущенного сигнала.

Сохранить существующий автоматический запуск ранее включённого host при
старте/unlock; проверить восстановление после сна/смены сети без второго daemon.
Не обещать непрерывный синк при приостановленном iOS-приложении: сигнал будет
обработан при следующей возможности клиента.

## Проверки и критерии готовности

1. На синтетической уже синхронизированной базе ~6600 Markdown-файлов проверить
   ноль изменений, одну и несколько изменённых заметок, удаление, rename/move,
   folder order/settings и создание conflict-файла. Отделить cold от warm run.
2. Успешный incoming push приводит к обновлению чистого GPUI buffer/navigation
   через событие; pending refresh не теряется при занятом shell. Проверить
   события старого профиля, lock/unlock и active folder workspace.
3. Dirty draft, baseline и пользовательский scroll сохраняются. Проверить
   одновременное редактирование/сохранение, incoming push и повторный запрос.
4. Искусственно медленная receipt maintenance не задерживает готовность host
   или уведомление о текстовых изменениях. Сохраняются hash verification,
   revocation и сериализация записи manifest с Git apply.
5. Простой shell не перечитывает все тела заметок раз в 3 с ради очередей.
   Использовать счётчики вызовов/чтений или инструментирование, а не flaky
   assertions на миллисекунды в unit tests.
6. Повторить подходящие проверки: `cargo test -p type-core --lib` для core,
   `cargo test -p type-gpui -- --test-threads=1` для GPUI, targeted formatting
   и `git diff --check`. Сокеты loopback могут требовать разрешённого запуска.
   Сборка dev bundle — если меняется runnable desktop, без автоматического
   перезапуска тестируемого пользователем приложения.

Добавлять тесты на реальные события, гонки и сохранность данных, а не тесты,
повторяющие структуру реализации. После успешных проверок не повторять их без
новых изменений/сомнений. Обновить `GPUI_MIGRATION_STATUS.md` фактическими
изменениями, результатами, commit id при коммите и оставшимися ограничениями.

Для замера разделить pre-commit/status, Git service, SSH close, push event,
UI reconcile и receipts. Логировать durations/counts и идентификатор цикла;
не добавлять содержимое заметок, личные пути или credentials. Инженерная цель
для небольших текстовых изменений при доступном peer — единицы секунд, но
достоверный end-to-end результат требует нового замера телефона и десктопа.

## Рекомендуемая последовательность реализации

1. Зафиксировать актуальный baseline и владельцев общих dirty files.
2. Подключить GPUI push event с coalescing и guards профиля/lock/drafts.
3. Отделить processing scans от refresh заметок.
4. Вынести receipts из startup/push notification; обеспечить безопасную очередь.
5. Проверить и исправить server/write coordination отдельным этапом.
6. После этого оптимизировать обновление по changed paths и согласовать
   optional desktop → phone revision signal с мобильным агентом.
7. Проверки, фактические замеры, обновление migration journal; без push/релиза.
