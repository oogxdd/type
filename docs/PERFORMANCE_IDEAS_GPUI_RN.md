# Идеи по производительности: GPUI и React Native

Дата: 2026-10-03.

ID сессии Codex: `01a102d9-e870-77f0-aef0-0700640da53f`.
В окружении одинаковое значение у `CODEX_THREAD_ID` и `CODEX_SESSION_ID`.

HEAD при записи документа: `18996dba9b61c17d52705a6ebd1b8e1f315574cc`.
Аудит проводился по текущим исходникам рабочего дерева; установленный бинарник
и мобильная сборка отдельно не проверялись. Номера строк со временем меняются.

## Контекст и приоритеты

- Пользователь доволен текущей производительностью GPUI.
- Хранилище пользователя содержит тысячи заметок. Это реальный масштаб для
  проверки мобильного кеша и списков, а не гипотетическое будущее расширение.
- Выводы основаны на чтении кода, без профилирования. Найденные операции могут
  давать задержки, но их вклад во время отклика пока не измерен.
- Tauri больше не входит в область этой работы.
- Раздел GPUI остаётся списком идей. Оптимизации RN ниже реализованы в рабочем
  дереве этой сессии; на телефоне их ещё нужно проверить.

## GPUI

### 1. Сократить получение всего текста при вводе

**Приоритет: небольшая полезная доработка; срочности нет.**

В обработчике `InputEvent::Change` дважды вызывается `EditorState::value()`:
для сравнения с сохранённым текстом и получения заголовка. В GPUI Kit 0.7.0
этот метод каждый раз собирает весь Rope в новую строку. HTML → Markdown уже
нет, но работа пропорционально длине документа происходит на каждом изменении.

Источник: [workspace.rs](../apps/gpui/src/workspace.rs), `ensure_editor`.

Возможные шаги:

- Сначала получать текст один раз на событие вместо двух.
- Затем проверить возможность вычислять заголовок по необходимым строкам Rope,
  без получения всего документа. Сохранить пропуск строк тегов и пустых строк.
- Пересмотреть определение `dirty`, сохранив корректное поведение при Undo,
  возвращающем текст к сохранённому состоянию.

Дополнительные кандидаты: `vim_key` получает весь текст перед обработкой
клавиши; отрисовка блочного курсора вызывает `value()` ради символа под курсором.
Проверять их отдельно, если длинные заметки начинают мешать вводу/навигации.

Источники: [main.rs](../apps/gpui/src/main.rs), `vim_key`;
[cursor.rs](../apps/gpui/src/cursor.rs), `render_cursor`.

### 2. Чтение и сохранение вне UI-потока

**Приоритет: отложить до воспроизводимых пауз или результатов измерения.**

Первое открытие незакешированной заметки синхронно читает файл из UI-контекста.
Автосохранение ждёт 400 мс, затем вызывает синхронный `flush` там же. Таймер
откладывает работу, но не переносит файловые операции на фоновый поток.

Обычный save читает тело для проверки конфликта; core снова читает файл для
сохранения frontmatter, записывает заметку, затем shell перечитывает её превью.
Общий refresh дерева и изменившихся превью уже выполняется в фоне.

Источники: [workspace.rs](../apps/gpui/src/workspace.rs), `ensure_editor`,
`schedule_save`, `try_flush`, `refresh`;
[backend.rs](../apps/gpui/src/backend.rs), `save`;
[core notes.rs](../crates/type-core/src/application/notes.rs), `write_note`.

Перенос на фон требует сохранить порядок записей, drafts при конфликтах,
актуальность результата после новых правок, переключение профилей и flush
перед уходом/закрытием/синхронизацией. При текущем хорошем отклике это не первая
задача только ради архитектуры.

### 3. Превью и теги

После успешного save перечитывается превью одной заметки внутри `flush`.
Кеш GPUI хранится в памяти; сериализации всего кеша в localStorage нет.

Теги всего активного документа разбираются после паузы 120 мс в UI-контексте.
Если появятся задержки на длинных документах, измерить этот путь вместе с вводом.

Источники: [workspace.rs](../apps/gpui/src/workspace.rs), `try_flush`;
[main.rs](../apps/gpui/src/main.rs), `schedule_tags`, `refresh_tags`.

## React Native: реализовано

### Открытие, сохранение и списки

- Открытие читает один путь через `readNoteIfExists`, без предварительного
  `getTree`. Отсутствие файла возвращает `null`; invalid path, locked и ошибки
  чтения остаются ошибками. Неудачный переход сохраняет предыдущую страницу.
- `CaptureSession.publish` отличает сохранённую ревизию от опубликованной.
  Повторное меню без правок не читает дерево/превью; уже завершившийся autosave
  всё равно обновляет заголовок при первом уходе. Ошибка публикации допускает
  повтор без лишней записи тела.
- Известная заметка перечитывает только собственное компактное превью.
  Новые пути, удаление и перемещения обновляют дерево. Неизменившиеся узлы и
  массивы сохраняют ссылки; карты превью подписаны отдельно по папкам.
- Feed хранит отсортированные строки в воркере: сортирует изменённые строки и
  сливает их с сохранённой историей. React получает только изменённые секции;
  ключи строк и ссылки остальных секций остаются стабильными. Изменение вне
  Stream не запускает Feed. Обновление календарных секций учитывает полночь и
  возвращение приложения в foreground.

Источники: [capture.ts](../apps/mobile/src/lib/capture.ts),
[note-pages.ts](../apps/mobile/src/lib/note-pages.ts),
[notes-store.ts](../apps/mobile/src/state/notes-store.ts),
[use-feed-sections.ts](../apps/mobile/src/lib/use-feed-sections.ts).

### Что выполняется в Rust, а что в воркере

**Rust / `spawn_blocking`:** работа с файлами, расшифровка, metadata и получение
двух строк Markdown-превью. Новый `list_note_summaries` ограничен 200 путями;
каждая строка ограничена 384 Unicode-символами. Тела обрабатываются по одному и
не передаются JS для списков. Прежний endpoint полных превью остаётся для других
потребителей. Правила Markdown, тегов, frontmatter, annotations, lens и
recording/handwriting проверяются общими JSON-примерами Rust и TS.

**Отдельный Worklet Runtime:** `JSON.parse` дерева/компактных превью/snapshot,
кеш превью, обработка Feed и `JSON.stringify` snapshot. Кеш обновляется
изменившимися записями; полная сериализация при необходимости остаётся в фоне.
Файловая запись snapshot выполняется асинхронным Expo FileSystem на стороне RN.

**RN JS / React:** жизненный цикл редактора, действия и подписки, согласование
ссылок дерева, слияние ограниченных порций и отображение виртуализированных
списков. Date labels вычисляются только для отображаемых строк.

Используется установленный Worklets 0.10.0:
`createWorkletRuntime({ name: "type-note-processing" })` + `runOnRuntimeAsync`.
Worker Runtime отдельный от UI Runtime анимаций. Worklet самодостаточный,
не захватывает React/Zustand/UniFFI/Expo-модули. Web и unit tests используют
те же чистые функции без нативного runtime.

Источники: [note_preview.rs](../crates/type-core/src/domain/note_preview.rs),
[FFI notes.rs](../crates/type-ffi/src/notes.rs),
[note-processing.ts](../apps/mobile/src/lib/note-processing.ts),
[note-worker.native.ts](../apps/mobile/src/lib/note-worker.native.ts).
Документация: [Runtime kinds](https://docs.swmansion.com/react-native-worklets/docs/fundamentals/runtimeKinds/),
[runOnRuntimeAsync](https://docs.swmansion.com/react-native-worklets/docs/threading/runOnRuntimeAsync/).

### Загрузка сегодняшних заметок и истории

Порядок: сегодня → текущая местная неделя (с понедельника) → заметки с неизвестной
датой → история Stream → обычные папки. Для приоритета используется дата из
кеша или имени файла. До чтения frontmatter это приближение: произвольно
переименованная старая заметка без кеша не имеет надёжной даты и попадает в
группу неизвестных.

Строки истории сразу доступны через кеш или placeholders; открытие выбранной
заметки идёт непосредственно в core и не ждёт обработки её превью. Между
пачками история уступает вводу и переходам меню/страниц. Уже начатую файловую
пачку не прерываем; результат проверяем перед публикацией. Смена профиля или его notes root и
блокировка сбрасывают оба кеша и инвалидируют запоздавшие результаты. Snapshot
дополнительно проверяет идентичность профиля и notes root при восстановлении.

Snapshot разрешён только при известном выключенном шифровании. Повреждённый
или старый формат игнорируется; версия формата теперь 2. При включении
шифрования snapshot активного профиля удаляется. Полные plaintext bodies
не записываются в preview cache.

Источник: [note-loading.ts](../apps/mobile/src/lib/note-loading.ts),
[notes-store.ts](../apps/mobile/src/state/notes-store.ts).

### Осталось измерить на устройстве

Функциональные проверки доказывают устранение повторной работы, но не величину
ускорения или FPS. Проверять на физическом телефоне: Release RN и оптимизированный
Rust (`codegen:ios:release` / `codegen:android:release`). Поскольку добавлены FFI
экспорты, нужны новые bindings и пересборка native client; одного OTA недостаточно.

Матрица одинаковых синтетических наборов: 1 000, 5 000 и 10 000 заметок, несколько
длинных документов, малая доля сегодня/на этой неделе. Сравнить холодный старт
без кеша, повторный старт, refresh без изменений, изменение одной/100 заметок
и sync во время загрузки. Измерять время до свежих строк, отклик открытия заметки
и меню, непрерывные интервалы JS, dropped frames и пиковую память.

Ручные функциональные проверки:

1. Десять раз открыть/закрыть меню без правок; затем изменить заголовок,
   дождаться autosave и открыть меню. Проверить новую и удалённую пустую заметку.
2. Во время догрузки истории печатать и открыть старую заметку. Проверить
   сохранение прокрутки и выделения при обновлении соседних строк.
3. Изменить дату/archived-маркер: строка перемещается/фильтруется корректно.
4. Проверить границу понедельника, полночь и изменение часового пояса.
5. Сменить профиль или заблокировать приложение во время загрузки. Старое
   содержимое не должно вернуться; при шифровании plaintext snapshot отсутствует.

Дополнительное дробление очень больших секций и запись кеша по отдельным
записям на диск остаются кандидатами по результатам этих замеров. Сейчас полная
сериализация снята с RN JS, но объём кеша и передача изменённой секции всё ещё
зависят от размера хранилища. Длинный контролируемый `TextInput` тоже остаётся
отдельным кандидатом на профилирование.

## Общие моменты

- Разделять два масштаба: тысячи заметок нагружают дерево/кеш/списки;
  большой отдельный документ нагружает ввод, парсинг и передачу тела.
- Измерять паузы UI/JS отдельно от общего времени файловых операций и sync.
  Долгий фоновый запрос не обязательно означает зависание интерфейса.
- Async-вызов не делает синхронную обработку текста или JSON фоновой.
- При оптимизации сохранять frontmatter, обработку конфликтов и порядок saves.
- Не сохранять plaintext previews при включённом шифровании. Сейчас мобильные
  snapshots разрешены только когда известно, что шифрование выключено.
- Проверки агентов использовать на синтетических профилях с тысячами заметок
  и разными размерами документов. Реальные ощущения UI проверяет пользователь.

## Выполненные проверки

- RN: 160 tests в 20 файлах: жизненный цикл, кеш, загрузка и worker jobs; тест на
  10 000 заметок и 100 прямых открытий закрепляет отсутствие `getTree`.
- Worker: реальная Babel worklet-трансформация и запуск сериализованной функции
  в изолированном JS runtime без захваченных модулей.
- TS contracts: 9 tests mobile-core и 77 tests shared, typecheck всех трёх пакетов.
- Rust: 96 library tests type-core и FFI end-to-end. Проверены отсутствующий
  путь, directory/invalid path, locked, bounded batch и компактный ответ для
  документа больше мегабайта. Сетевые тесты core прошли вне sandbox, поскольку
  sandbox запрещает их временные локальные сокеты.
- На Mac сгенерированы iOS simulator bindings/xcframework. Expo собрал iOS
  Hermes bundle с native entry и новым Worker Runtime.

Основные команды:

```sh
npm run test -w @typenotes/mobile
npm run test -w @typenotes/mobile-core
npm run test -w @typenotes/shared
npm run typecheck -w @typenotes/mobile
npm run typecheck -w @typenotes/mobile-core
npm run typecheck -w @typenotes/shared
cargo test -p type-core --lib --offline
cargo test -p type-ffi --offline
npm run codegen:ios -w @typenotes/mobile-core
```

Физическое iOS/Android устройство, native UI runtime и performance benchmarks
GPUI не проверялись. Приложение пользователя не запускалось и не перезапускалось.
