# Как добавить фичу: две обвязки и кодген

Практическая шпаргалка: что нужно трогать (и что НЕ нужно) при разных видах
изменений, что на самом деле делает `ubrn`-кодогенерация и где на границе
Rust ↔ JavaScript живёт сериализация.

## Быстрая карта: что менять при каком изменении

| Что меняешь | Где правишь | Кодген нужен? |
|---|---|---|
| Только UI десктопа | `apps/desktop/src` | нет |
| Только UI мобилки | `apps/mobile/src` | нет (Expo Go / демо-режим работают на моке) |
| Общий TS (типы, frontmatter, превью) | `packages/shared` | нет — оба приложения импортируют исходники напрямую, сборки у пакета нет |
| Бэкенд-фича для обоих приложений | `crates/type-core` + две обвязки (чек-лист ниже) | только для реальной нативной сборки мобилки |
| Бэкенд-фича только для десктопа | `crates/type-core` + Tauri-команда | нет, никогда |

Ключевая асимметрия: **десктопный путь кодгена не имеет вообще.** Tauri-команда
регистрируется макросом и работает сразу после `cargo build`. Кодген — сугубо
мобильная история, и то не на каждый чих (см. ниже).

## Чек-лист: новая бэкенд-функция от ядра до обоих UI

Логика пишется один раз в `crates/type-core` (как устроено ядро внутри —
глава [04](./04-how-to-change-code.md)). Дальше — две тонкие обвязки.
Для примера возьмём существующую `read_note`; новая функция проходит
ровно те же точки.

**Десктоп (работает сразу, кодгена нет):**

1. Tauri-команда в `apps/desktop/src-tauri/src/commands/<домен>.rs` —
   ~10 строк: залочен ли экран, собрать сервис, вызвать.
2. Строчка в `generate_handler![]` в `commands/mod.rs`
   (`notes::read_note,`).
3. TS-обёртка в `apps/desktop/src/features/<фича>/api/` через `invokeLogged`.

**Мобилка (4 файла руками):**

4. Экспорт в `crates/type-ffi/src/<домен>.rs`:

   ```rust
   #[uniffi::export(async_runtime = "tokio")]
   pub async fn read_note(path: String) -> Result<String, CoreError> {
       run_blocking(move || notes_service()?.read_note(&path)).await
   }
   ```

5. Метод в интерфейсе `RawCore` (`packages/mobile-core/src/raw-core.ts`),
   имя в camelCase: `readNote(path: string): Promise<string>`.
   Опечатку или пропуск здесь ловит CI (`scripts/check-ffi-surface.mjs`).
6. Типизированный фасад в `core-api.ts` — превращает JSON-строки в типы из
   `@typenotes/shared/types`, чтобы экраны не видели JSON.
7. Реализация в `mock-core.ts` — иначе демо-режим и тесты мобилки отстанут
   от настоящего ядра.

**Кодген (только когда собираешь настоящий нативный модуль):**

8. На Маке: `npx ubrn build ios --config ubrn.config.yaml --and-generate`
   в `packages/mobile-core` (подробности — README пакета).

Чего делать **не** надо:

- Логику в обвязках. Команда и FFI-экспорт — это ~10 строк диспетчеризации;
  если хочется написать больше, место этому в `application/` ядра.
- Править что-либо в `src/generated/` — оно перезаписывается кодгеном и
  не лежит в git.
- Заводить типы границы где-то кроме `@typenotes/shared/types` — JSON-формы
  у Tauri IPC и FFI одни и те же, и типы на них тоже одни.
- Гонять кодген «на всякий случай» после каждой правки. Он нужен строго
  перед сборкой приложения на симулятор/устройство, если с прошлой сборки
  менялся `crates/type-ffi`.

## Что на самом деле делает кодген

JavaScript на телефоне не умеет звать Rust напрямую. Между
`readNote("Feed/x.md")` в React Native и Rust-функцией лежит обвязка:
превратить JS-строку в Rust-`String` через C-интерфейс и обратно, прокинуть
асинхронность (tokio ↔ Promise), превратить `Err(CoreError)` в JS-исключение,
зарегистрировать функции в рантайме React Native (JSI). Это сотни строк
однообразного кода на каждую функцию, на двух языках. Их и генерирует `ubrn`.

Работает так: атрибут `#[uniffi::export]` при компиляции зашивает в библиотеку
метаданные («есть функция `read_note`, принимает String, возвращает String,
кидает CoreError, асинхронная»). `ubrn` собирает `crates/type-ffi` под
Apple/Android-таргет, вычитывает метаданные и генерирует:

| Куда | Что | Зачем |
|---|---|---|
| `src/generated/` | TypeScript | `readNote(path): Promise<string>` (snake_case → camelCase автоматически) + упаковка аргументов и превращение ошибок в исключения |
| `cpp/generated/` | C++ | JSI-клей: регистрирует функции в рантайме RN и переправляет вызовы в Rust-библиотеку |
| `ios/`, `android/` | проекты нативных библиотек | чтобы Rust скомпилировался и слинковался в приложение |

Чего кодген **не** генерирует — и почему остаётся ручная работа:

- **`raw-core.ts` рукописный не случайно.** Сгенерированный код существует
  только после прогона на Маке и в git не коммитится. А компилироваться
  проект должен всегда — в CI, в Expo Go, без Мака. Поэтому есть рукописный
  интерфейс `RawCore` — стабильное «обещание» того, что сгенерирует кодген, —
  и против него компилируется всё остальное (фасад, мок, приложение).
  Приложение никогда не импортирует сгенерированный модуль напрямую:
  на старте один раз вызывается `setRawCore(...)` либо с настоящим модулем,
  либо с моком.
- `core-api.ts` и `mock-core.ts` — тем более рукописные: первый знает типы
  предметной области, второй — поведение для демо-режима.

Расхождение руками поддерживаемого с настоящим стерегут две CI-джобы
(`.github/workflows/ffi-bindings-check.yml`): дешёвая `surface` сверяет список
`#[uniffi::export]`-функций с методами `RawCore` на каждом PR, задевающем шов;
Mac-джоба `codegen` (пока ручной запуск) реально гоняет `ubrn` и проверяет,
что каждый метод `RawCore` существует в сгенерированном.

## Локальная разработка мобилки с настоящим ядром (не мок)

Мок — это только «нулевая передача»: UI-работа в Expo Go и тесты. Чтобы
разрабатывать против настоящего Rust-ядра, нужен **dev-клиент** (Expo
development build) — собранное один раз приложение, в которое вшита
Rust-библиотека. Дальше повседневная разработка — обычный hot reload.

Один раз (на Маке):

1. Кодген: `npm run codegen:ios` в `packages/mobile-core` (перед первым разом —
   `npm install --no-save uniffi-bindgen-react-native@0.31.0-3` там же).
   Скрипт собирает `--sim-only` — только слайсы под симулятор, это вдвое
   меньше cargo-работы; перед установкой на физический телефон нужен
   `npm run codegen:ios:device`.
2. В `apps/mobile/src/core/boot.ts` раскомментировать импорт сгенерированного
   модуля (`setRawCore(generated)`) — он закомментирован, пока кодгена не
   было, потому что Metro резолвит импорты статически.
3. `npm run prebuild -w @typenotes/mobile`, затем
   `npm run ios -w @typenotes/mobile` — ставит dev-клиент на
   симулятор/устройство.

Дальше цикл разработки такой:

- **Правишь TypeScript** (`apps/mobile/src`, `packages/shared`,
  `packages/mobile-core/src` кроме `generated/`) → обычный
  `npm run start -w @typenotes/mobile`, hot reload в уже установленный
  dev-клиент. Никакого кодгена, никакой пересборки — так проходит почти вся
  работа над мобилкой, уже с настоящим ядром и настоящими файлами на диске.
- **Правишь Rust** (`type-core` или `type-ffi`) → пересборка dev-клиента
  одной командой из корня: `npm run mobile:ios` (кодген + `expo run:ios`).
  Это нужно даже если сигнатуры не менялись (логика внутри библиотеки — та,
  что была на момент сборки).

Почему так: dev-клиент состоит из двух слоёв. Нативный «контейнер» (движок
RN, Expo-модули, JSI-клей и Rust-библиотека, статически слинкованная в
бинарник машинным кодом) заморожен в момент Xcode-сборки. JS-бандл в
dev-режиме в приложение не вшит — он тянется с Metro-сервера при старте,
поэтому hot reload подменяет только его. «Пересобрать dev-клиент» = собрать
и переустановить `.app` (первая сборка долгая, дальше cargo и Xcode
инкрементальны — минута-другая; данные приложения при переустановке
сохраняются). Десктопная аналогия: Vite HMR против «`tauri dev`
перекомпилирует и перезапускает бинарник» — здесь «перезапустить бинарник»
означает переустановить приложение на устройстве.

Без Мака: iOS-сборка невозможна в принципе (Xcode). Обходные пути —
Android-dev-клиент (`npm run codegen:android` работает и на Linux, нужен NDK)
или облачная сборка EAS Build (раннеры-маки; кодген придётся встроить шагом
сборки, потому что `generated/` не лежит в git).

## День разработчика: три петли

Раст нигде не хот-релоадится — ни в Tauri, ни в React Native. Это свойство
компилируемого кода, а не выбора фреймворка. Поэтому рабочий режим строится
вокруг трёх петель обратной связи, от быстрой к медленной:

| Петля | Команда | Цена итерации |
|---|---|---|
| Логика раста | `cargo test -p type-core --lib` | секунды, без приложения |
| Живая обкатка раста — десктоп | `npm run desktop:tauri dev` | React — Vite HMR мгновенно; Rust — `tauri dev` сам пересобирает и перезапускает окно (~15–60 с, ручных команд нет) |
| Проверка на телефоне | `npm run mobile:ios` | минуты, вручную |

Следствия:

- `type-core` framework-free и юнит-тестируется, поэтому основная отладка
  раста должна жить в первой петле — это главный ежедневный дивиденд
  гексагональной архитектуры.
- Десктоп — правильный «обкаточный» шелл: раст, проверенный там, — **тот же
  код**, что поедет на телефон (мобильно-специфичного раста почти нет,
  только тонкие JSON-обёртки `type-ffi`).
- Третья петля нужна раз в фичу, а не раз в правку.

Типичная фича целиком:

1. Логика + тесты в `type-core` — петля 1, секунды.
2. Tauri-команда, потыкал вживую в десктопе — петля 2, автоматом.
3. FFI-экспорт + `raw-core.ts` + `core-api.ts` + `mock-core.ts` — пять минут
   механики, дрейф ловит CI.
4. Мобильный экран — на hot reload: против мока (метод уже есть в
   `mock-core`) или против старого dev-клиента для остальных функций.
   Раст не трогается — пересборок нет.
5. Один раз `npm run mobile:ios` — проверка на телефоне.

## «А я слышал, в новом React Native сериализацию убрали»

Частый повод для сомнений, поэтому разберём честно.

**Что именно убрали.** В старом React Native между JS и нативным кодом стоял
асинхронный «мост» (bridge): каждый вызов сериализовался в JSON-сообщение,
складывался в батч и переезжал в другой мир. Новая архитектура (JSI +
TurboModules) заменила это прямыми C++-вызовами: JS-значения читаются из
JS-движка напрямую, без обязательного JSON-этапа на каждый вызов.

**Мы уже на новой архитектуре.** `ubrn` генерирует именно JSI/TurboModule-код —
тот самый `cpp/generated/`. Старого моста в пути «экран → Rust» нет.

**Где сериализация всё же есть — и будет в любом дизайне.** «Без сериализации»
на границе Rust ↔ JS не бывает: у JS-объекта и Rust-структуры разные
представления в памяти, «передать по ссылке» нельзя. Вопрос только в формате
и в том, кто пишет код перегонки:

- Наш выбор: составные аргументы/результаты — **JSON-строки** (те же формы,
  что у Tauri IPC). Через FFI едет одна строка, по краям — `serde_json` и
  `JSON.parse`.
- Альтернатива uniffi: описать DTO как uniffi Records — тогда типы границы
  проверяет компилятор, но данные всё равно сериализуются, просто в бинарный
  `RustBuffer` вместо JSON-текста. Плюс пришлось бы вести второй набор DTO
  в Rust и потерять симметрию с Tauri.
- И сам Tauri IPC на десктопе — тоже JSON между WebView и Rust. То есть
  десктоп живёт ровно на том же принципе, и это никого не смущает.

**Цена вопроса.** Наши полезные нагрузки — заметка, дерево папок, список
превью: десятки килобайт максимум. `JSON.parse` таких объёмов — доли
миллисекунды; на фоне файловых операций и git это не измеримо. Единственное
по-настоящему тяжёлое место — аудио, которое едет как base64 внутри JSON
(`readRecordingAudio`); если оно когда-нибудь станет медленным, именно его
первым стоит перевести на бинарный путь (или отдавать путь к файлу вместо
содержимого). Пока — не стоит.

**Вывод:** решение «JSON-строки на границе» — не унаследованная ошибка старого
RN, а осознанный размен: минус — компилятор не проверяет формы JSON (это
слабое место №2 в главе [08](./08-shared-code-review.md), прикрыто тестами),
плюс — один набор TS-типов на оба приложения и мост ценой ~10 строк на
функцию.
