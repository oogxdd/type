# Что общее, а что раздельное: ревизия монорепы

Снимок на июль 2026, после того как из Tauri-приложения вырезали всё
мобильное/iOS/OTA (мобильное приложение теперь — React Native в `apps/mobile`).
Здесь: сколько кода реально общее, почему граница проведена именно так, какие
у этой схемы слабые места и что предлагается сделать.

## Цифры

Строки кода без тестов:

| Кусок | Строк | Чей |
|---|---|---|
| `crates/type-core` — Rust-ядро | 10 313 | **общий** |
| `packages/shared` — общий TypeScript | 1 077 | **общий** |
| `crates/type-ffi` + `packages/mobile-core` — мост к мобилке | 1 624 | только мобилка |
| `apps/mobile` — React Native UI | 2 094 | только мобилка |
| `apps/desktop/src-tauri` — Tauri-обвязка | 687 | только десктоп |
| `apps/desktop/src` — React UI десктопа | 19 307 | только десктоп |

Как это читать:

- **Во всей репе** общий код — примерно **треть** (~11 400 из ~35 100).
- **С точки зрения мобилки** — из того, что она исполняет, **~75% общее**
  (11 400 общих против 3 700 своих).
- **Если смотреть только на логику** (выкинуть оба UI) — **~83% общее**.
  Всё "не общее и не UI" — это два тонких транспорта: Tauri-обвязка (687 строк)
  и FFI-мост (1 624 строки).

Самый большой необщий кусок — React UI десктопа. Это осознанно: десктоп — богатое
трёхпанельное приложение (drag-and-drop, командная палитра, линза, настройки),
а мобилка — намеренно минимальный "открыл и печатаешь" интерфейс.

## Почему граница именно такая

Правило одно: **всё, что может испортить данные, написано один раз — на Rust.**
Git-синк и разруливание конфликтов, шифрование/блокировка/panic-сброс, очереди
транскрипции и OCR, профили и настройки, именование файлов, миграции — у всего
этого ровно одна реализация в `type-core`. Двум реализациям такой логики нельзя
дать разъехаться, поэтому второй просто нет.

UI не общий — тоже осознанно. `react-dom` и `react-native` не могут делить
компоненты (разные примитивы: `div` против `View`), а продуктово мобильный UX
и не должен повторять десктопный. Общее спущено на уровень ниже: оба UI берут
из `packages/shared` одни и те же типы данных, разбор превью, frontmatter,
константы системных папок.

Швы между слоями маленькие:

- Ядро от платформы хочет только `AppEnv` — два пути к директориям.
- FFI говорит теми же JSON-формами, что и Tauri IPC → один набор TS-типов
  обслуживает оба приложения, и новая бэкенд-фича стоит "одна реализация в ядре
  плюс две обёртки по ~10 строк".

## Слабые места — на пальцах

### 1. «Тройная бухгалтерия»: одну бэкенд-фичу надо прописать в трёх местах

Как сейчас выглядит добавление функции бэкенда (скажем, `rename_profile`):

1. Пишешь логику в `crates/type-core`. Один раз — это хорошо.
2. Выставляешь её десктопу: Tauri-команда в
   `apps/desktop/src-tauri/src/commands/` (~10 строк) плюс строчка в
   `generate_handler![]`.
3. Выставляешь её мобилке: экспорт в `crates/type-ffi` (~10 строк).
4. **Руками** дописываешь её сигнатуру в
   `packages/mobile-core/src/raw-core.ts` — это TypeScript-описание того,
   какие функции есть в нативном модуле. Оно ниоткуда не генерируется,
   его поддерживает человек.
5. Перегенерируешь сам нативный модуль утилитой `ubrn` — локально это можно
   сделать **только на Маке**. Mobile TestFlight CI делает это на GitHub macOS
   runner и запрещает production-сборку, если остался demo entry.

Опасность в шагах 4–5. Если забыть шаг 4 (или опечататься в имени) — TypeScript
мобилки уверен, что функция есть, а её нет: десктоп работает, мобилка падает
в рантайме с "function not found". Если забыть шаг 5 — то же самое, только
падение случится у того, кто соберёт приложение со старым нативным модулем.
Дешёвая surface-проверка и macOS release codegen теперь ловят эти два класса
ошибок; отдельная FFI codegen job всё ещё нужна для проверки каждого PR до
релиза.

**Что сделано / предлагается:**

- **Сделано:** скрипт-сверка `scripts/check-ffi-surface.mjs` — парсит список
  `#[uniffi::export]`-функций в `type-ffi` и сравнивает с методами интерфейса
  `RawCore` в `raw-core.ts`. Разошлись — CI красный. Гоняется в
  `.github/workflows/ffi-bindings-check.yml` на каждом PR, задевающем шов.
  Это закрывает шаг 4.
- **Сделано (драфт):** в том же workflow есть Mac-джоба `codegen`, которая
  реально гоняет `ubrn`-кодогенерацию и проверяет, что каждый метод `RawCore`
  существует в сгенерированных биндингах (закрывает шаг 5). Пока запускается
  только вручную (`workflow_dispatch`). Отдельно production workflow
  `.github/workflows/mobile-testflight.yml` уже успешно гоняет полный device
  codegen на `macos-26` и проверяет отсутствие demo fallback.
  После первого успешного ручного прогона её можно перевести на автозапуск
  по PR.
- До обкатки Mac-джобы шаг 5 остаётся пунктом в чек-листе PR
  (см. гочу "Two shells, one core" в AGENTS.md).

Пошаговый чек-лист добавления фичи и разбор того, что именно делает кодген
(и когда он вообще нужен), — в [главе 9](./09-adding-features-and-codegen.md).

### 2. На границе с мобилкой компилятор типы не проверяет

FFI-функции принимают и возвращают **JSON-строки**. Это сделано специально:
формы JSON те же, что у Tauri IPC, поэтому один набор TS-типов подходит обоим
приложениям, и мост получился очень дешёвым. Цена: компилятор не может
проверить, что Rust и TypeScript согласны о форме JSON — расхождение всплывёт
только в рантайме или в тестах.

Менять архитектуру из-за этого не нужно (e2e-тест на настоящем ядре уже есть),
но полезно понимать: **надёжность этой границы обеспечивается тестами и
конвенцией, а не типами.** Дёшево усилить: маленькие тесты сериализации на пары
"Rust-структура ↔ TS-тип" для самых ходовых форм (заметка, профиль, git-статус).

### 3. Кое-какая логика написана дважды

- **Жизненный цикл черновика заметки** — самое заметное. Правила "создать файл
  лениво при первом непустом тексте, сохранять с debounce, дописать при уходе
  с экрана, удалить опустевшую заметку" реализованы дважды: на десктопе в
  `use-note-editor` (React/Tiptap), на мобилке в `lib/capture.ts`. Правила
  одинаковые, код разный. Поменяешь одно — обязан вспомнить про второе.
  Предложение: **при следующем изменении этих правил** (не заранее) вынести
  их в платформенно-нейтральную машину состояний в `packages/shared`.
- Мелкое: `findFolder` в мобильном `lib/feed.ts` дублирует `findNode` из
  десктопного `tree-ops`; `effectiveTranscriptionMode()` реализован и в Rust,
  и в TS (осознанно — чтобы UI мог показать режим без похода в ядро, но это
  два места с одним правилом); `mock-core.ts` — по сути третья мини-реализация
  поведения ядра для демо-режима и тестов, может отставать от настоящего.

## Что стоит сделать (по приоритету)

1. **`git_password` — убрать из синкаемого файла.** Сейчас пароль git лежит
   открытым текстом в `.type/settings.json` **внутри папки заметок** — то есть
   синкается на все устройства и попадает в git-историю. Перенести в
   device-local `config.json` (он уже существует для API-ключей и не синкается),
   со чтением-фолбэком из старого места.
2. **Удалить мёртвый порт нативного рекордера из ядра.** Методы
   `native_capabilities`/`start_native`/`stop_native` остались от Tauri-iOS;
   теперь их не зовёт никто (RN пишет звук через expo-audio).
3. **Убрать две неиспользуемые Tauri-команды** (`queue_recording_transcriptions`
   с AssemblyAI и `export_profiles_to_documents`) — их фронтенд десктопа больше
   не вызывает, это мобильные сценарии, живущие теперь в FFI.
4. **FFI-сверка** из пункта про тройную бухгалтерию — скрипт и workflow уже
   есть; осталось обкатать Mac-джобу ручным запуском.
5. **Легаси-миграции** (`use-legacy-profile-sync-migration`, фолбэк
   `mobile_auto_transcription_enabled`, переименования папок) — не трогать
   сейчас; удалить одним заходом, когда все живые установки точно мигрировали.

## Можно ли выносить в shared не только типы, но и хуки?

Можно. React в `react-dom` и `react-native` — **один и тот же React**:
`useState`, `useEffect`, `useCallback`, zustand — всё работает одинаково.
Хук нельзя шарить только если он трогает браузерное: `window`, `document`,
`localStorage`, `CustomEvent`, DOM-элементы — или напрямую импортирует
Tauri-`invoke`.

Приятный факт: `packages/shared` собран **без** библиотеки типов `dom` в
tsconfig. Положишь туда код с `window` — `tsc` не соберётся. То есть граница
"здесь только платформенно-нейтральное" защищена компилятором, а не договорённостью.

Рецепт выноса всегда один: хук переезжает в shared, а платформенные вещи
(объект API, хранилище, подтверждение "точно удалить?") получает параметрами.

Кандидаты по состоянию на сейчас:

| Кандидат | Что мешает | Вердикт |
|---|---|---|
| Чистые обходчики дерева (`findNode` и часть `tree-ops`) | ничего — уже чистые функции | **да, можно сразу**: мобилка уже дублирует `findFolder` |
| Механика черновика (`use-note-editor` ↔ `capture.ts`) | надо выделить ядро-правила из React/Tiptap-обвязки | **да, но при следующем изменении правил** |
| `use-processing-queue` / `use-auto-queue-loop` (опрос очередей) | завязаны на `window.setInterval` и `CustomEvent` — нужен шов для событий | когда у мобилки появится UI очередей, не раньше |
| `use-ssh-key` (жизненный цикл SSH-ключа) | `confirmAction` (браузерный confirm) + прямой `invoke` | да, если мобильный SSH-экран начнёт дублировать логику |
| `use-git-sync-workflows` ↔ мобильный `sync-store` | мобильная версия **намеренно** проще (65 строк против 268) | нет: не тащить десктопную сложность в мобилку |
| zustand-сторы (selection, appearance) | ничего технического | нет: сторы отражают конкретный UI, общего смысла в них мало |

Общий принцип: сейчас реального дублирования в TS мало, и это нормально.
Правильный триггер для выноса в shared — **"второе использование уже
разъехалось с первым"** или "появилось третье", а не "вдруг пригодится".
Преждевременный вынос даёт слой косвенности, который потом мешает менять
каждый UI независимо — а независимость UI здесь и была целью.
