# 01. Зачем вообще нужна архитектура

Архитектура — это способ управлять изменениями. Не красота ради красоты, не
сложные диаграммы, не "enterprise". Просто договоренность: где живет какая
ответственность и кто от кого зависит.

## Проблема без слоев

В небольшом приложении легко писать так:

```text
кнопка -> handler -> прочитать файл -> распарсить markdown -> проверить пароль -> записать файл
```

Сначала это быстро. Потом появляются вопросы:

- Как протестировать создание заметки без Tauri?
- Как заменить файловую систему на базу данных?
- Как переиспользовать backend-логику в мобильной оболочке?
- Почему изменение в Git sync ломает заметки?
- Где искать правило: "нельзя создавать заметки внутри Recordings"?

Когда код растет, проблема не в том, что файлов много. Проблема в том, что
ответственности перемешаны.

## Что дает clean / hexagonal architecture

Идея очень простая: важные правила приложения должны быть внутри, а детали
технологий — снаружи.

Внутри:

- что такое заметка;
- как создать заметку;
- какие папки системные;
- когда надо обновлять порядок;
- как выглядит результат операции.

Снаружи:

- Tauri IPC;
- `std::fs`;
- `git2`;
- шифрование;
- HTTP API;
- iOS native APIs.

## Почему зависимости должны смотреть внутрь

Если use case зависит напрямую от Tauri, его трудно использовать без Tauri.
Если use case зависит напрямую от `fs`, его трудно тестировать без диска.
Если use case зависит напрямую от `git2`, Git начинает протекать в бизнес-логику.

Поэтому мы хотим такую форму:

```text
Tauri command
  вызывает application service
    который зависит от port trait
      который реализует adapter
```

Важно: это не значит, что весь код становится абстрактным. Абстракция нужна
там, где она защищает важный сценарий от внешних деталей.

## Почему это хорошо именно для Type

Type — local-first приложение. У него много внешних деталей:

- notes лежат как `.md` файлы;
- Git sync работает через `git2`;
- encryption держит ключ в памяти;
- iOS recording использует native APIs;
- Whisper provision делает Python environment;
- import запускается в worker thread.

Если все это смешать в command handlers, backend станет трудно менять. Слои
позволяют сказать: "создание заметки — это use case, а файловая система — только
один способ его выполнить".

## Главное правило

Когда пишешь код, спрашивай:

> Это правило приложения или техническая деталь?

Если это правило приложения — оно ближе к `application` / `domain`.
Если это техническая деталь — оно ближе к `adapters`.
