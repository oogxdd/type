# 07. Кэш превью заметок на фронтенде

Эта глава — про слой данных фронтенда: как устроен кэш превью, кто и когда его
инвалидирует, и почему мы (пока) не взяли TanStack Query.

Контекст: Feed и списки заметок строятся из **превью** — заголовок, вторая
строка, даты, флаги (архив, recording, OCR). Превью нельзя получить из одного
имени файла: нужны front matter и первые строки тела. Значит, для отрисовки
фида нужно "что-то знать" про каждую заметку — и это что-то надо кэшировать,
иначе каждый запуск приложения начинается с полного скана хранилища.

## Поток данных

```text
get_tree (лёгкий: только имена/пути, тел не читает)
   │
   ▼
list_note_previews([paths])   ← один batch IPC на весь список
   │  на каждую заметку: одно чтение файла → body + meta
   ▼
parseNotePreview (TS)         ← shared/lib/format.ts
   │
   ▼
buildFeedTree / списки        ← features/notes/navigation/model/feed-tree-model.ts
```

Ключевые файлы:

- `src/features/notes/list/hooks/use-note-previews.ts` — весь кэш живёт здесь.
- `src/features/notes/navigation/state/use-notes-tree-state.ts` — вызывает хук,
  передаёт ключи профиля и флаг шифрования.
- `src-tauri/src/application/notes.rs` (`list_note_previews`) — batch-команда.
- `src/shared/lib/storage.ts` — префикс ключа localStorage и функция очистки.

## Три уровня кэша

1. **In-memory** — `cacheRef: Map<path, { updatedMs, preview }>` внутри
   `use-note-previews`. Живёт, пока смонтировано дерево. Сравнение по
   `updatedMs` решает две задачи: не перепарсивать неизменённые заметки и
   сохранять **идентичность объектов** превью (мемоизированные строки списка
   не ререндерятся).

2. **localStorage** — снапшот распарсенных превью, один ключ на профиль:
   `notes-viewer-note-previews-v1:<profileId>`. Хранится только результат
   парсинга (~200 байт на заметку), **тела заметок не персистятся**. При
   записи снапшот мержится с существующим и чистится по живому списку путей
   (`allNotePaths`), чтобы обновление одной папки не выбрасывало превью
   остальных, а удалённые заметки не копились.

3. **Stale-while-revalidate** — порядок на каждом запуске/обновлении:
   нарисовать из кэша сразу → дёрнуть batch в фоне → молча заменить
   изменившееся. Видимый "Loading feed..." остаётся только при самом первом
   запуске, когда снапшота ещё нет.

Относительные подписи дат ("yesterday") пересчитываются при гидрации из
localStorage — сами подписи в снапшоте протухают, а timestamps нет.

## Инвалидация: шина CustomEvent

Типизированного слоя инвалидации нет — есть два window-события:

| Событие | Кто диспатчит | Кто слушает | Эффект |
|---|---|---|---|
| `notes-tree-invalidated` | `use-note-editor` (после сохранений/переименований) | `use-notes-tree-state` | `refreshTree()` → новое дерево → батч превью перезапрашивается |
| `note-previews-invalidated` | `use-notes-tree-actions` (CRUD), `recordings-context` и `handwriting-context` (через `use-processing-queue`, когда завершилась транскрипция/OCR), `use-desktop-editor-pane` | `use-note-previews` | очистка in-memory кэша + refetch батча |

Это **самое слабое место слоя**: события нетипизированы, их список размазан по
семи файлам, и узнать "кто инвалидирует превью" можно только grep'ом. Пока
событий два — терпимо. Если появится третье-четвёртое, см. раздел про
TanStack Query ниже.

## Смена профиля

`resetKey` (= `profileId:notesRoot`) полностью **заменяет** in-memory кэш на
снапшот нового профиля (или пустую Map). Это исключает протекание превью
между профилями даже при совпадающих относительных путях (`Feed/note.md` есть
в обоих).

## Инвариант шифрования

Превью — это plaintext-заголовки заметок. Поэтому:

- при включённом шифровании `persistKey = null` → персист выключен полностью;
- `enableSecurity` (security-context) вызывает `clearPersistedNotePreviews()`
  и вычищает снапшоты, записанные до включения шифрования;
- panic-wipe чистит весь localStorage и так.

**Если меняешь слой персиста — этот инвариант обязан пережить изменение.**
Тела заметок и plaintext-превью не должны оказаться в localStorage у
зашифрованного хранилища ни при каком сценарии.

## Почему здесь нет TanStack Query (решение от 2026-06-10)

Вопрос рассматривался, когда чинили производительность фида. Решение —
**не брать сейчас**. Аргументы зафиксированы, чтобы не пересматривать с нуля.

Что TQ дал бы из коробки (и что мы написали руками):

- stale-while-revalidate, кэш по ключу (`['previews', profileId]`),
  дедупликация запросов;
- `invalidateQueries()` вместо шины CustomEvent — типизировано и в одном месте;
- `persistQueryClient` вместо ручного localStorage-слоя;
- `refetchInterval` для поллинга очередей транскрипции/OCR
  (`use-auto-queue-loop`);
- devtools.

Почему всё-таки нет:

1. **Перф-проблема была не в кэше.** Тормозил бекенд: per-note IPC, git-walk
   по истории на каждую заметку, чтение тел в `get_tree` на главном потоке.
   TQ оркестрирует фетчи, но не делает их дешевле — batch-команда и лёгкое
   дерево были бы нужны в любом случае.
2. **Дефолты TQ заточены под сеть** (retry, refetchOnWindowFocus,
   networkMode), а у нас локальный IPC за миллисекунды — почти всё пришлось
   бы выключать.
3. **Сложность фронтенда — в производном графе**, а не в фетчах:
   tree → allNotes → feedSourceNotes → previews → feedTree → selection.
   TQ покрывает только нижний слой; мемоизация, контексты и связь с
   selection остаются как есть. Выигрыш меньше, чем кажется.
4. **Ловушка персиста:** `persistQueryClient` по умолчанию сохранил бы сырой
   ответ `list_note_previews` — то есть полные тела заметок. Наш ручной слой
   хранит только распарсенные превью и выключается при шифровании. С TQ это
   решается кастомным persister'ом, но это ровно та деталь, которую легко
   упустить и получить plaintext в localStorage.

Когда решение стоит пересмотреть (триггеры):

- событий-инвалидаций становится больше двух и шина CustomEvent начинает
  болеть;
- появляются новые поллинг-поверхности кроме очередей транскрипции/OCR;
- начинается миграция на React Native / UniFFI — TQ одинаково работает в RN,
  и единый слой данных поверх UniFFI-вызовов станет сильным аргументом.

Если внедрять — инкрементально: сначала запросы tree + previews, производные
модели не трогать, persister кастомный (только распарсенные превью, с
отключением при шифровании — инвариант выше).
