# Native iOS GitHub Actions to TestFlight (without EAS)

This is the operations runbook for `.github/workflows/mobile-testflight.yml`.
Expo generates the native project on a GitHub-hosted macOS runner, but Expo/EAS
does not build, sign, or submit the app. Xcode and App Store Connect perform
those steps directly.

## Release flow

```text
mobile-vX.Y.Z tag / manual dispatch
  -> macos-26 runner + Xcode 26.6
  -> npm checks + Rust/UniFFI device framework
  -> expo prebuild + CocoaPods
  -> unsigned intermediate xcarchive
  -> Xcode cloud-signed App Store export -> Type.ipa
  -> altool validate + upload
  -> Apple processing -> existing Type RN TestFlight app
```

Repository-specific values:

| Item | Value |
| --- | --- |
| App Store Connect app | `Type RN` |
| Main bundle ID | `com.typenotes.mobile` |
| Widget bundle ID | `com.typenotes.mobile.RecordingWidget` |
| Workspace / scheme | `apps/mobile/ios/Type.xcworkspace` / `Type` |
| Export options | `apps/mobile/ExportOptions.plist` |
| Apple team | `Y377P5XKGJ` |
| Xcode | 26.6 |

The workflow creates an **unsigned intermediate archive** with
`CODE_SIGNING_ALLOWED=NO`. This is intentional: the ephemeral runner has no
local Apple Distribution private key. `xcodebuild -exportArchive` then uses the
team App Store Connect API key and automatic signing to obtain the app and
widget App Store profiles and produce a signed IPA. The IPA, not the
intermediate archive, is validated and uploaded.

This exact flow was proven locally on 2026-08-12 for both bundles. Apple server
validation returned `VERIFY SUCCEEDED with no errors`, and build
`0.2.3 (2026081201)` was accepted by App Store Connect (delivery UUID
`bef9469f-6809-41cd-9447-5093e3b1f594`).

## One-time Apple setup

Confirm that:

1. Apple Developer membership and App Store Connect agreements are current.
2. The existing `Type RN` app uses `com.typenotes.mobile`.
3. explicit identifiers exist for the app and
   `com.typenotes.mobile.RecordingWidget`;
4. the App Store Connect API key is a team key with permission to upload builds
   and perform automatic provisioning.

The widget target is generated by
`apps/mobile/modules/recording-activity/plugin/withRecordingActivity.js` during
`expo prebuild`. It needs its own identifier and provisioning profile.

No `.p12`, local Apple Distribution certificate, temporary Keychain, or
`EXPO_TOKEN` is needed for this workflow. Do not reuse the desktop
`APPLE_CERTIFICATE`: it is unrelated to iOS App Store signing.

## GitHub environment and secrets

The `ios` job uses the `testflight` GitHub Environment. Store these four values
as environment or repository secrets:

| Secret | Contents |
| --- | --- |
| `APPLE_TEAM_ID` | Apple Developer team ID (`Y377P5XKGJ`) |
| `APP_STORE_CONNECT_KEY_ID` | Team API key ID |
| `APP_STORE_CONNECT_ISSUER_ID` | Team API key issuer ID |
| `APP_STORE_CONNECT_PRIVATE_KEY` | Complete `AuthKey_<KEY_ID>.p8` contents |

The environment is already configured in repository `oogxdd/type`. The three
API-key values are environment secrets; `APPLE_TEAM_ID` already exists as a
repository secret and is also available to the job. GitHub displays only names
and update timestamps after upload; secret values cannot be read back.

For a new repository, configure them from a trusted Mac. Feed values through
stdin so the private key is not placed in command arguments:

```sh
printf '%s' '<team-id>' \
  | gh secret set APPLE_TEAM_ID --env testflight --repo oogxdd/type
printf '%s' '<key-id>' \
  | gh secret set APP_STORE_CONNECT_KEY_ID --env testflight --repo oogxdd/type
printf '%s' '<issuer-id>' \
  | gh secret set APP_STORE_CONNECT_ISSUER_ID --env testflight --repo oogxdd/type
gh secret set APP_STORE_CONNECT_PRIVATE_KEY --env testflight \
  --repo oogxdd/type < /secure/path/AuthKey_<KEY_ID>.p8
```

A required reviewer may be added to the environment if releases should pause
for approval before Apple credentials become available.

## Implementation details

The workflow:

1. parses `mobile-vX.Y.Z`, or validates manual version/build inputs;
2. checks out the repository and selects Xcode 26.6;
3. runs mobile typechecking/tests;
4. generates the Rust/UniFFI device framework;
5. refuses to continue if the device framework/package entry is missing or
   still points at the demo core;
6. runs `expo prebuild` and CocoaPods;
7. writes the `.p8` secret to Xcode's standard private-key directory;
8. archives without code signing;
9. exports with automatic cloud signing;
10. validates and uploads the resulting IPA with `altool`;
11. retains the IPA as a GitHub artifact.

`MOBILE_VERSION` and `IOS_BUILD_NUMBER` are present before `expo prebuild`, so
`apps/mobile/app.config.js` writes them into the generated app Info.plist. The
archive command also supplies `MARKETING_VERSION` and
`CURRENT_PROJECT_VERSION`, which covers the widget target and guards against
generated Xcode defaults.

`apps/mobile/ExportOptions.plist` intentionally lives outside generated
`apps/mobile/ios/`: Expo prebuild can recreate that directory. Likewise, the
recording-activity Expo config plugin adds `-lz -liconv` to the generated Pods
aggregate xcconfigs so the Rust static library links on a clean runner.
The job also exports `IPHONEOS_DEPLOYMENT_TARGET=16.4` while building Rust so
vendored libgit2/OpenSSL objects and the final library target the same minimum
iOS version as the app.

## Cutting a release

For a tagged release from `main`:

```sh
git switch main
git pull --ff-only
git tag mobile-v0.2.4
git push origin mobile-v0.2.4
```

For a controlled first run, use Actions -> **Mobile TestFlight** -> **Run
workflow** from `main`, supply a semantic version, and optionally supply a
unique numeric build number. A manual dispatch uploads to TestFlight but skips
the GitHub Release job. GitHub Release metadata is created only when a new
`mobile-vX.Y.Z` tag is pushed; additional TestFlight build numbers for the same
version reuse that existing release.

Apple identifies a build by bundle ID, marketing version, and build string.
Releasing the same marketing version again requires a new build number. A
rerun of one GitHub run reuses `github.run_number`, so use a new manual dispatch
with an explicit number if the previous build reached Apple.

An upload first appears as processing in App Store Connect. It does not by
itself add the build to every tester group. Internal automatic distribution can
be configured in App Store Connect; external testing may require Beta App
Review.

## Verification

The Actions log should show:

- Xcode 26.6 selected;
- successful app and widget compilation;
- `Exported Type` from `xcodebuild -exportArchive`;
- `VERIFY SUCCEEDED with no errors`;
- `UPLOAD SUCCEEDED with no errors` and a delivery UUID.

After upload, check App Store Connect -> TestFlight -> Build Uploads. Verify the
version/build and wait for processing to finish before assigning testers.

## Common failures

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Export cannot create profiles | API key lacks provisioning access or an identifier is missing | Use a suitable team key and register both bundle IDs |
| Widget signing failure | Widget identifier/profile is missing | Provision `com.typenotes.mobile.RecordingWidget`; do not reuse the app profile |
| `expo-modules-jsi` compile error | Wrong Xcode selected or stale local DerivedData | Confirm Xcode 26.6; clean DerivedData for a local retry |
| Undefined `crc32`, `iconv`, or zlib symbols | Config-plugin linker patch was not applied | Confirm generated `Pods-Type.release.xcconfig` includes `-lz -liconv` |
| Wrong app or widget build number | Release env was absent during prebuild | Confirm `MOBILE_VERSION` and `IOS_BUILD_NUMBER` in the job environment |
| Duplicate build | Version/build pair already reached Apple | Dispatch a new run with a different numeric build number |
| Build uploaded but absent in TestFlight | Apple is still processing it or processing failed | Check Build Uploads and the delivery log |
| Local `codesign --verify` reports an untrusted authority | Cloud-managed signing certificate is not trusted in the local Keychain | Use App Store Connect server validation; do not treat the unsigned archive as the distributable artifact |
