TLDR: Feed действительно «просто файлы по датам», но чтобы получить эти даты, приложение сейчас на **каждую** заметку делает два IPC-вызова с полным чтением файла, а внутри `get_note_meta` ещё и обходит **всю git-историю репозитория** — синхронно на главном потоке. Плюс фронтенд перестраивает всё feed-дерево после каждой загруженной заметки. Отсюда и долгая загрузка, и фризы интерфейса.

## Почему так долго — по убыванию вклада

**1. Git-walk на каждую заметку (главная причина).** `get_note_meta` безусловно вызывает `note_timestamps` (`src-tauri/src/application/notes.rs:166`), даже когда `created_ms`/`updated_ms` уже лежат в front matter (а у заметок, созданных приложением, они есть всегда — git-результат просто выбрасывается). А `git_note_timestamps_from_history` (`src-tauri/src/adapters/git/mod.rs:454`) открывает репозиторий и проходит **все коммиты от HEAD**, делая по два tree-lookup на коммит. То есть стоимость ≈ N заметок × C коммитов. При 300 заметках и 1000 коммитах синка — сотни тысяч tree-lookup'ов. Кэш есть, но ключ включает HEAD oid — после каждого pull/push всё считается заново.

**2. Это блокирует главный поток.** Команды notes — обычные синхронные `#[tauri::command]` (`src-tauri/src/commands/notes.rs:82`), в отличие от git_sync/local_sync, которые ходят через `run_blocking_command`/`spawn_blocking`. Git-walk выполняется прямо на main thread — отсюда «тормозит интерфейс», а не просто «долго грузится».

**3. 2N IPC-вызовов и двойное чтение файла.** `use-note-previews.ts` для каждой заметки делает `getNoteMeta` (который читает и парсит весь файл) и затем `readNote` (читает весь файл ещё раз, расшифровывает и гонит **полное тело** через IPC-мост как JSON) — а нужны только две строки превью. Конкурентность 6, так что всё это ещё и выстраивается в длинную очередь.

**4. O(N²) на фронтенде.** Каждое разрешённое превью вызывает `setNotePreviews` → новый объект `allNotePreviews` → инвалидируется memo `buildFeedTree` (`use-notes-tree-state.ts:157`) → полная пересборка и сортировка feed-дерева → новое значение `NotesTreeContext` → ререндер всех потребителей. N заметок = N полных пересборок дерева из N заметок.

Бонус: кэш превью живёт только в памяти (`cacheRef`) — каждый запуск приложения полностью холодный, а событие `note-previews-invalidated` сбрасывает его целиком.

## Альтернативы

**Вариант A (рекомендую): один батч-вызов на бекенде.** Новая команда вида `list_note_previews` — за один IPC Rust проходит Feed-папку и возвращает массив `{path, title, preview (2 строки), created_ms, updated_ms, archived, note_type, …}`. Парсинг front matter тысяч файлов в Rust — миллисекунды; полные тела через мост не гоняются вообще. Это ровно ваша ментальная модель: «листинг файлов с датами». Сделать команду async через `run_blocking_command`, чтобы не трогать main thread.

**Вариант B (обязателен в любом случае): убрать git из горячего пути.** Минимум — вызывать `note_timestamps` только когда front matter не содержит дат, с fallback'ом на mtime файла вместо git. Если git-даты всё же нужны (заметки с другого устройства без front matter) — один общий revwalk, который за один проход истории заполняет map дат для *всех* файлов, вместо walk-на-заметку.

**Вариант C (косметика сверху):** батчить обновления превью на фронте (накапливать и флашить раз в ~100мс вместо setState на каждую заметку — убирает O(N²)); персистить кэш превью в localStorage/IndexedDB для мгновенного отображения при старте со stale-while-revalidate; виртуализация списка, если заметок тысячи.

A+B убирают ~95% проблемы: загрузка Feed становится одним быстрым вызовом, дозагрузки нет, интерфейс не блокируется. C имеет смысл делать только частично (персистентный кэш приятен, батчинг становится почти неактуален, когда превью приходят одним ответом). Скажи, если делать — начну с A+B.

**Фикс** (только `feed-tree-model.ts`):
- подписи дней недели (7 штук), месяцев (12) и диапазонов недель кэшируются — `toLocaleDateString` вызывается единицы раз вместо десятков тысяч;
- календарный скелет месяца строится один раз на месяц, а не на каждую заметку;
- все сортировки используют один общий `Intl.Collator` вместо `localeCompare` на каждое сравнение (тот же порядок, в ~10 раз быстрее).

Результат на том же бенчмарке: **1000 заметок — 20мс, 3000 — 30мс** (~140–290× быстрее). Все 60 тестов и `tsc` зелёные; существующие тесты `feed-tree-model` подтверждают, что структура и порядок дерева не изменились. Переключение вкладки теперь должно быть мгновенным.
